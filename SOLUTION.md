# Rewarding novelty Solution 
Hackathon theme: user generated content. Problem: reward the novelty of a text
submission made against a fixed piece of content, on a normalized [0.0, 1.0]
scale, while never rewarding novel content that is not relevant to that fixed
content. 

## 1. The content

**Fixed content** (97 words): a product listing for *Boho*, a fictional project
management tool for small agencies. Boards, timelines, client portals, time
tracking, integrations, apps, pricing, trial. See `data/fixed_content.json`.

**User submission**, three user-provided properties:

| Field | Type | Role |
|---|---|---|
| `headline` | text | extracted for claims, with the body |
| `body` | text | main source of claims |
| `recommend` | `yes` / `no` / `mixed` | echoed in the breakdown, not scored |

`recommend` is not a novelty signal. A verdict is not information, and scoring it
would let a "no" review game novelty on a corpus of "yes" reviews.

**Other submissions**: 50 synthetic reviews in `data/corpus.json`, generated by an
LLM during setup, ordered by submission time. About ten themes recur (easy UI,
client portal, time tracking, Slack, pricing, mobile app, support, Gantt,
reporting, onboarding) so the pool has real redundancy, plus a dozen one-off
points so "already said by exactly one earlier review" is testable.

## 2. How a submission is scored

```
submission:
[1] near-copy?   Jaccard(word set of headline+body, any earlier review) >= 0.70
    yes -> final = 0.0, duplicate_of = <id>
    no ->
    [2] extract claims: LLM (Gemini) sees the listing; returns {claim, on_topic} per atomic claim; JSON output, disk-cached
    [3] per claim: on_topic == false -> status = irrelevant (can never be "new")
        relevance = share of claims with on_topic == true
        gate = ramp(relevance, GATE_LO, GATE_HI)
        (cos(claim, listing) is recorded per claim as a diagnostic; it is not scored)
    [4] per on-topic claim:
          candidates = the K_JUDGE known claims with the highest cosine to this claim
          sim        = cosine of the nearest one
          sim >= HIGH        -> known   (decided by cosine alone)
          sim <  LOW         -> new     (nothing in the pool is close)
          LOW <= sim < HIGH  -> Gemini judge "same point?", asked for each candidate
                                with cosine >= LOW, nearest first (cached, required)
                                  any candidate judged same -> known
                                  none                      -> new
        novelty   = n_new / n_claims           (irrelevant claims dilute, never count)
        substance = min(1, n_new / K)          (one new fact should not equal four)
        final = gate * novelty * substance
```

**Known claims** are the atomic claims of the listing itself plus the claims of
every earlier review. Order matters: a review is scored against what existed when
it was submitted, then its on-topic claims join the pool.

**Every score explains itself.** The output is a `ScoreBreakdown` with the four
factors and a per-claim table: the claim, whether it was on topic, its status
(`new` / `known` / `irrelevant`), how that was decided (`relevance` /
`cosine_high` / `cosine_low` / `judge`), and the closest known claim with its
source review id and cosine. `python -m novelty.cli score --body "..."` prints it.

## 3. Design rationale

**Novelty is measured on claims, not on text.** Two reviews can share almost no
words and make the same point, or share most words and make opposite points.
Extracting atomic claims and matching them individually is what lets a review earn
credit for the one new thing it says among five repeated ones.

**Relevance is judged by the extractor, not by embedding distance.** The first
design used cosine(claim, listing). Run 01 (`runs/01-baseline.md`) showed it
measures "sounds like the listing": restating the listing scored 0.6 to 0.78, while
on-topic complaints ("Support is email-only", 0.14; "The mobile app crashes
constantly", 0.06) were indistinguishable from off-topic sentences ("The drip tray
fills up quickly", 0.16). No threshold separates them, and a nearest-known-claim
variant fails too because a truly novel claim is far from everything by
definition. The extractor already reads the listing, so asking it "is this claim
about this product?" costs nothing extra and separated the two groups completely
from the first run.

**Per-claim relevance, not only a review-level gate.** Off-topic claims are tagged
before the novelty step and stay in the denominator, so padding a rehash with novel
but irrelevant sentences lowers the score. Two padded/unpadded pairs in the golden
set lock this in.

**Embeddings decide the easy cases, an LLM judge decides the hard band.** MiniLM
cosine above 0.80 or below 0.40 is reliable. Between, a threshold cannot tell a
paraphrase from an opposite-polarity claim about the same feature, which is
exactly the distinction that matters. The judge is asked only there, on up to
three candidates, with temperature 0 and a disk cache keyed on the exact pair, so
every decision is reproducible. In the final run, 39 of 84 claims reached the
judge; 26 were settled by cosine alone; 19 were off topic.

**Product name neutralised before embedding.** "Boho is easy to use" and "The tool
is easy to use" should be neighbours. Run 03 (`runs/03-product-name-regression.md`)
showed the opposite failure too: when every claim starts with the product name,
MiniLM clusters on the name and the true matches fall out of the candidate set.
Replacing the name with "the product" in the embedded text, symmetrically on both
sides, fixed both directions. The breakdown still shows the original wording.

**A substance term.** Novelty is a share, so one unseen fact in a one-line review
would score 1.0, the same as four. `min(1, n_new / 2)` holds a one-liner to 0.5
without penalising a two-fact review.

**Near-copy detection with Jaccard, and only there.** Word overlap is a good
fingerprint for copy-paste of a 40 to 80 word review. It is a bad one for 5 to 10
word claims, where a single word swap moves it a lot and a paraphrase scores near
zero. So it runs on whole reviews as step 1 and nowhere else.

## 4. Success criteria and achievement

Criteria were written into SPEC.md before the first run.

| # | Criterion | Result |
|---|---|---|
| 1 | Every golden item lands in its category's band | **22/24**: the 21 agent-written items (21/21 in run 04; runs 01-03: 12, 18, 16) plus three items added afterwards, two of which are known gaps kept as expected failures (section 8) |
| 2 | min(novel_relevant) > max(rehash, restatement, duplicate) | 1.000 > 0.125 |
| 3 | max(novel_irrelevant) < min(novel_relevant) | 0.000 < 1.000 |
| 4 | Every padded item <= its unpadded twin | 0.000 <= 0.000, both pairs |
| 5 | Every score explainable from `per_claim` alone | yes; see `runs/04-calibrated.verbose.txt` |
| 6 | One submission against the 50-review pool under 1 s with a warm cache | yes |

Golden categories (`data/golden.json`):

| Category | n | Band | Proves |
|---|---|---|---|
| duplicate | 2 | 0.0 and flagged | near-copies earn nothing |
| rehash | 4 | <= 0.25 | paraphrasing common points earns little |
| listing_restatement | 1 | <= 0.25 | the listing itself is known |
| novel_relevant | 4 | >= 0.6 | unseen on-topic facts are rewarded |
| mixed | 3 | 0.2 to 0.8 | half-new reviews land in the middle |

The one non-zero rehash (0.125) is "Boho is very affordable for a small shop"
judged different from "Boho is inexpensive". Debatable, and capped by substance.

## 5. What did not work, and what changed

| Run | Change | Result | Lesson |
|---|---|---|---|
| 01 | cosine-to-listing relevance, sentence-split listing, top-1 judge | 12/21 | cosine to the listing is not relevance |
| 02 | extractor on-topic flag, atomic listing claims, top-3 judge | 18/21 | judge too strict on generalisations; paraphrases sat just under LOW |
| 03 | judge prompt with rules and examples, LOW 0.50 to 0.40, "name the product" extraction rule | 16/21 | the shared name token hijacked nearest-neighbour search |
| 04 | naming rule reverted, product name neutralised for embedding | 21/21 | fix the embedding text, not the extraction text |
| 06 | no change; two author-written items added: g23 (informal on-topic complaint with one new point, relabelled mixed, 0.600) and g24 ("the logo is cute", labelled trivial, scores 0.500) | 22/23, 1 known gap | g24 kept as a strict expected failure rather than relabelled; see section 8 |

### 5b. Order matters: replaying the corpus

`python -m novelty.cli replay` scores the 50 corpus reviews in submission order,
each against only the reviews before it (`runs/05-replay.txt`).

| Slice | Mean final | Reviews at 1.0 |
|---|---|---|
| first 10 | 0.901 | |
| first 25 | 0.840 | 14 |
| last 25 | 0.662 | 7 |
| last 10 | 0.692 | |

The first review scores 1.0 against a pool that holds only the listing. Reviews
that make a first-of-its-kind point score 1.0 wherever they sit (r011 calendar
duplicates, r016 no recurring tasks, r022 CSV-only export, r036 API rate limit,
r047 no templates). Reviews that restate earlier themes fall as the pool fills:
r012 "Clean UI, happy clients" 0.167 after r001 and r006 made both points; r034
"Support improved but still slow" 0.167 after r005 and r017; r043 "a breath of
fresh air" 0.167 after nine earlier reviews praised the interface.

## 6. Automated tests

`python -m pytest`: 50 tests, 48 pass and 2 are expected failures (g24 and g25, section 8).

- `test_text.py`: tokenisation, Jaccard, sentence splitting, product-name neutralisation.
- `test_scoring.py`: unit contract for every pure scoring function, with a fake judge; proves the judge is consulted only in the borderline band and only on candidates above LOW.
- `test_golden.py`: one test per golden item plus the three ordering properties and the padded-pair property.
- `test_ordering.py`: the first review scored against an empty pool beats the same text submitted after 49 others; a re-submission is caught as a duplicate; average score falls from the first half of the corpus to the second.

Golden and ordering tests need `GEMINI_API_KEY` and are skipped without it. All
Gemini responses are committed in `data/cache/gemini.json`, so the suite makes no
new calls on a clean checkout.

## 7. Reproduce

```
python -m pip install -e ".[dev]"
cp .env.example .env            # add GEMINI_API_KEY
python -m novelty.cli golden -v   # 24 golden items with breakdowns
python -m novelty.cli replay      # corpus in submission order
python -m pytest
```

## 8. Limitations

- **A single aesthetic remark can earn up to 0.5.** "The logo is cute" is extracted
  as an on-topic claim; nothing in the pool mentions the logo; the substance term
  caps it at 0.5 rather than 0. Kept as a strict expected failure (g24).
- **A point restated across headline and body counts twice.** Claims of one
  submission are compared with the pool, never with each other, so a headline that
  paraphrases the body yields two new claims and the substance term rises from 0.5
  to 1.0. Exact repetition is absorbed by the extractor, and so are some paraphrases,
  but not all: the workload pair in g25 doubles. Not in
  the problem statement, so recorded as a strict expected failure (g25) rather than
  fixed. The fix is a within-submission repeat check using the same cosine bands
  and judge as step 4.
- **Extraction is not perfectly stable across near-identical inputs.** A text and
  its padded twin can yield slightly different claim sets, so pair comparisons carry
  some noise. Both pairs currently score 0.000 vs 0.000; a tolerance may be needed
  if the corpus grows.
- **The golden set is small and was mostly written by the same agent that designed
  the scorer.** 21 of 23 items. Thresholds were tuned on it across four runs, so
overfitting to these 23 texts is possible. The two author-written items were
  the check on that, and one of them found a real gap on the first try.
- **Gemini is required.** Claim extraction, the on-topic verdict and the borderline
  judge are LLM calls. Determinism comes from temperature 0 plus a committed cache,
  not from the model; a different model or a prompt change re-opens calibration.
- **Thresholds are specific to all-MiniLM-L6-v2.** LOW 0.40 and HIGH 0.80 were read
  off this model's cosine distribution and would need re-checking for any other.
- **Judge cost grows with pool size.** Each on-topic claim in the borderline band
  can cost up to K_JUDGE calls. Cached per pair, so re-scoring is free, but a
  production pool of thousands of reviews would want a vector index and a cheaper
  first-pass filter.
- **Near-copy detection only catches copies.** Whole-review paraphrases pass step 1
  by design and are handled claim by claim, which is slower.
- **English only, one product.** Nothing is language-specific in the code, but the
  prompts, the corpus and the calibration are all English and all Boho.

## 9. Coding agent disclosure

Claude Code (model Claude Fable 5.1) was used throughout. The human wrote the
one-page spec first, then directed the agent to set up the project, generate the
data, produce a skeleton with the scoring math left as stubs, and later to
calibrate, and document. The human wrote the initial scoring functions,
merged two of them, removed the offline judge, questioned the use of an LLM judge
over Jaccard, and added golden items of their own. Each calibration run was pasted
back and the agent's diagnosis and proposed change were approved or rejected
before being made; one proposal (the naming rule) regressed and was reverted.
[WORKLOG.md](WORKLOG.md) has the division of work, how the agent was directed, the
key decisions and who made them, and what the agent got wrong.
